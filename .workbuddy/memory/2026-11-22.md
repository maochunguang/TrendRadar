## NAS 借腾讯云 Lighthouse 恢复 GitHub 榜单（合规路线：数据接口，非代理）

背景：绿联 NAS（DX4800 Plus，192.168.3.215）访问 github.com 不通，TrendRadar 容器的 GitHub 日/周/月榜长期抓不到。
合规判断：在腾讯云上跑 gost/SSH 代理违反腾讯云服务协议 5.7(7)「非法代理服务器(Proxy)」与 5.7(10)「擅自建立非法定信道进行国际联网」，
并触碰《计算机信息网络国际联网管理暂行规定》第 6/14 条。改用「云服务器自己抓、NAS 来取」的数据接口形态，规避信道性质。

### 架构
TrendRadar 容器 → http://172.17.0.1:1201 → NAS 上的 nas-tunnel 容器（ssh -L）
→ 腾讯云 127.0.0.1:8081（trending-api）→ github.com

### 云端（Lighthouse lhins-0ggfh6ve，ap-shanghai，122.51.13.223，Ubuntu 22.04 / Python 3.10）
- 代码：/opt/trending-api/trending_server.py（纯标准库，5 分钟缓存，解析规则对齐 TrendRadar）
- 服务：/etc/systemd/system/trending-api.service，已 enable，只监听 127.0.0.1:8081
- 授权：/root/.ssh/authorized_keys 装了专用隧道公钥，带
  `restrict,port-forwarding,permitopen="127.0.0.1:8081",command="/bin/false"`
- 会话侧无 SSH 密码；日常改动走 Lighthouse TAT（MCP execute_command）

### NAS 侧
- /volume2/docker/nas-tunnel/{Dockerfile,entrypoint.sh,key/id_ed25519,data}
- 镜像 nas-tunnel:latest（alpine 3.20 + openssh-client，约 12MB）
- 容器 nas-tunnel，--restart unless-stopped，-p 1201:1201
- 私钥 /volume2/docker/nas-tunnel/key/id_ed25519（专用，非用户主密钥）

### TrendRadar 配置
- /volume2/docker/trendradar/config/config.yaml → github.mirror_url: http://172.17.0.1:1201
- 备份：config.yaml.bak-mirror-202611221152
- 结果：[GitHub] 获取 40 条榜单数据，output/html/github.html 正常生成

### 踩过的坑（重要）
1. **GitHub trending URL 正确写法是 `/trending?since=daily`**。`/trending/daily` 会被当作 language 过滤参数，返回空列表
   （页面提示「we don't have any trending repositories for your choices」）。
   TrendRadar 源码 `TRENDING_BASE_URL = "https://github.com/trending/{since}"` 本身就是错的，它的一级直连从未成功过。
2. **`restrict` 不禁止登录 shell**——它只管转发/pty/agent。要真正锁死必须再加 `command="/bin/false"`。
   验证时 `echo SHOULD_NOT_RUN` 曾成功执行，加入 command 后才被拒。
3. **验证 permitopen 不能只看本地端口是否监听**。`ssh -L` 会先在本地 listen，越权端口探测本机也会成功。
   必须发真实数据并看 `ssh -v` 输出，被拒时是 `channel open failed: administratively prohibited`。
4. AI 新星榜（api.github.com Search API）在 NAS 上直连是通的，不需要镜像；NAS 只是 github.com 网页端不通。
5. 容器 env 里 GITHUB_TOKEN 为明文（已提醒用户轮换）。
